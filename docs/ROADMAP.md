## 2026-10-25 필기+사진 및 필기 교정 준비

사용자 결정: iPad에서 전부 필기로 작성하는 실험을 계속 발전시키고 사진도 붙인다. 초기 필기 일기는 필기 교정만 허용한다. **필기 교정은 실제 앱에 적용하지 않고 대비만 한다.** 필기→텍스트 인식→기존 사람/AI 교정은 후속 방안을 검토한다.

이번 구현은 네트워크를 차단한 `/local-lab` 안에만 있다. 제품 기능 플래그 diary/correction/textRecognition은 모두 false. 기존 서버 migration/RPC와 유료 AI는 변경하지 않았다. 모듈0.2.0/labVersion2가 없는 설치본에는 재빌드 안내만 표시한다.

- 고정 문서 좌표768×1024. 필기 화면과 사진 preview가 같은 좌표계를 쓰며 사진은 앞서 만든 5종 모양·자르기·두 손가락 회전/확대 컴포넌트를 재사용한다. 사진 조절과 필기를 명시적으로 전환해 입력 충돌을 피한다. 현재 페이지 자체의 독립 확대/스크롤은 잠가 필기와 사진의 좌표가 어긋나지 않게 했다.
- 문서별 native draft와 JS 사진 manifest 분리. 필기700ms·사진400ms 자동저장, 명시적 저장에서 drawing 원본/투명 ink-only PNG/사진 포함 합성 PNG를 생성한다. content hash 기반 snapshot으로 동일 내용 재저장 파일 중복을 줄인다. 손상된 저장값은 빈 문서로 덮지 않는다. 기존 단일 필기는 lab-main 문서에서만 이어받는다.
- 교정 실험 시작 시 원문 snapshot과 사진 배치를 복제·고정한다. 교정 획은 다른 storageKey의 빨간 필기 레이어이며 자체 undo/redo를 가진다. 원문을 이후 바꾸어도 기존 교정의 배경은 바뀌지 않는다. 교정 계속/현재 원문으로 새 교정 구분. 사진 삭제 시 기존 교정 snapshot이 쓰는 파일은 바로 지우지 않는다.
- 제품 서버 연결 전에 문서/계정 소유권, source revision 잠금, 교정자별 asset 권한, 보존·삭제, 전체 문서 export 정리를 설계해야 한다. 로컬 실험 파일을 그대로 공용 Storage에 업로드하지 않는다. 현재는 iPad가 아닌 기기로 결과를 보내는 실제 교정 왕복이 아니다.

### 텍스트 인식 후 기존 교정으로 확장하는 순서

1. 인식 입력은 사진·교정 획을 제외한 원문 필기 snapshot만 사용한다. 원본 PKDrawing과 사진 포함 preview는 그대로 보존한다.
2. 언어를 명시하여 인식하고 줄별 텍스트·문서좌표·인식 신뢰도(엔진이 제공할 때)를 보관한다. OCR의 자동 언어 보정은 꺼서 학습자의 문법 실수가 인식 과정에서 사라지지 않게 한다.
3. 작성자에게 원문과 인식문을 함께 보여주고 확인을 받는다. 인식 오독과 원래 문법 오류를 구분한다. 확인한 텍스트만 기존2,000자 제한과 문장 분리 규칙을 적용한다.
4. 서버에 별도 text transcription revision을 만들고 원본 handwriting revision/hash에 고정한다. 이 revision의 sentence IDs로 기존 사용자 교정/AI 교정을 호출한다. 기존 save_diary_revision의 하루1개 제한을 우회하는 새 일기 생성이나 가짜 content를 사용하지 않는다. 별도 attach-transcription 계약이 필요하다.
5. 처음 결과는 원문 옆의 텍스트 교정으로 제공한다. 단어를 원문 획 위에 정확히 겹치는 UX는 줄/단어 좌표 및 stroke ID 대응 검증 뒤에 확장한다. 원문이 변경되면 미확정 인식 결과를 폐기하고 기존 결과는 당시 revision에 유지한다.

`contracts.ts`에 source/hash 일치·작성자 확인·2,000자 검사를 하는 candidate 어댑터를 준비했다. 실제 OCR 엔진·전송 버튼·서버 API는 연결하지 않았고 readyToSubmit=false이다. 인식문을 자동으로 문법 교정해 작성자의 원문을 바꾸지 않는다.

검증 계획: 동의받은 합성/테스트 필기 각 언어30페이지에서 글자 오류율(CER), 작성자 수정 시간, 의도적 문법 오류 보존, 사진 포함/미포함 차이, p50/p95 인식시간, 메모리·모델 디스크 용량을 비교한다. 엔진별 confidence를 같은 척도로 간주하지 않는다. 읽지 못한 줄을 문맥으로 지어내거나 결과 정확도를 수치 없이 통과로 표시하지 않는다.

## 전체 실행 과업과 디자인 적용 전 목표 — 2026-10-25

사용자 요청: 대화 전체와 플로우차트 범위를 묶어, 모든 대상 화면의 기능을 먼저 완결하고 디자인을 적용할 수 있는 상태로 만든다. 이 절은 실행 과업 정리이며 구현 완료 기록이 아니다. 기존 F01–F27·S01–S14·V01–V29와 연결하고 별도 기능 번호 체계를 만들지 않는다.

### 현재 판단

- 서버: 인증·가입·토큰·공개 글·댓글·관계·편지의 기반과 권한/동시성 검사가 앞서 있다. 그러나 교본 저장, 교정 선점 수명과 작업 복구, 푸시 전송, 신고 운영, 계정/파일 정리, AI 비용 제어와 필기 저장은 제품 완결에 필요한 서버 과업이다. 사소한 수정만 남았다고 분류하지 않는다.
- 클라이언트: 이미 API에 연결된 화면이 많다. 추가 기능·상태·복구·화면 연결·기기별 동작과 디자인 적용의 범위가 넓다. 전체 재작성 대신 기능별 repository와 기존 화면을 확장한다.
- AI: 호출과 파싱 기반은 있지만 실제 품질·지연·비용의 합격 여부는 아직 모른다. UI 개발량보다 실험과 평가의 불확실성이 크다.
- 디자인·실기기 검증: 기능 구현과 별개의 완료 축이다. 화면이나 API 개수로 전체 완료율·남은 기간을 산출하지 않는다.

### 중간 완료 기준: 디자인 적용 대기

각 화면에서 아래 항목을 모두 확인한 뒤에만 기능 준비로 표시한다. 시뮬레이터·오프라인 검사만 한 경우 실제 기기 미확인을 함께 표시한다.

- [ ] 진입·뒤로 가기·딥링크·권한 만료 후 복귀 경로가 연결된다.
- [ ] 실제 API로 조회·저장·수정·삭제가 해당 기능 범위에서 동작하고 재진입해도 결과가 유지된다. 샘플 응답 화면은 API 연결 완료가 아니다.
- [ ] 정상·로딩·빈 결과·실패·오프라인·접근 불가 상태와 다시 시도/취소 동작이 있다.
- [ ] 연타·중복 요청·세션 변경·앱 종료/재실행에서 중복 차감·저장 유실·다른 계정 정보 노출을 막는다.
- [ ] 화면 표현과 데이터 조회·변경·상태 전이가 분리되어 있고 디자인 변경이 API/정책을 다시 구현하게 만들지 않는다. 공통화를 위해 전체 앱을 재작성하지 않는다.
- [ ] 입력·키보드·스크롤·오류 포커스·접근성 이름·기본 터치 영역을 확인한다. 최종 대비·간격·기기별 배치는 디자인 적용 후 다시 확인한다.
- [ ] F행에 코드, 실행 검사, 실기기 미확인, 남은 디자인을 따로 적는다. 기능 흐름·정보 구조를 바꾸는 새 디자인은 영향 검토가 필요하며 무조건 외형만 교체하면 된다고 약속하지 않는다.

유료 AI·실제 푸시·필기 기기가 필요한 흐름은 대체 응답으로 화면을 검증할 수 있지만 실제 연동 확인 전에는 전체 기능 준비로 표시하지 않는다. 디자인 준비, 기능 준비, 실기기 통과, 출시 가능을 하나의 완료 상태로 합치지 않는다.

### 실행 순서와 첫 묶음

1. 교정 선점/반납·실패 복구와 AI/사람 상태·읽음을 서버와 S05/S07/S08에서 함께 완결한다. 반납 RPC 등 기존 구현부터 확인하며, 만료/환급 값은 미정 정책으로 명시한다.
2. 교본 카드 계약·서버 저장/조회/삭제→S08 저장→S09 목록→S03 홈 복습을 한 왕복으로 구현한다. 저장 단위/보존 정책 결정이 필요하면 독립 가능한 화면 상태·계약 검사를 먼저 준비한다.
3. 가입/작성 세부 복구 및 전체 화면 진입·빈/오류 상태를 채운다. AI 평가 자료/오프라인 도구·비용 통제 준비와 미확정 디자인의 흐름 검토를 병행한다.
4. 알림·푸시·신고·계정 운영을 서버와 클라이언트에서 함께 완결한다. 승인/기기 의존은 분리한다.
5. 실제 Pencil 기기 실험은 초기에 병행하고 성공 뒤 제품 연결한다. 기본 화면이 끝날 때까지 필기 위험 확인을 미루지 않는다.
6. 기능 준비된 화면부터 디자인을 적용하고 기능별 기기 검사를 이어간다. 마지막에 전체 왕복·성능·설치/운영 조건을 확인한다.

첫 구현 묶음의 결과물은 교정 화면의 나가기/반납/복귀와 출처별 상태, 해당 API/정책의 차이 및 오류/중복 검사다. 작업 중 정책 입력이 필요한 부분만 따로 남기고 승인된 독립 구현을 계속한다. 시간별 자동화는 삭제 상태를 유지한다.
