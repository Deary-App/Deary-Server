# Deary 커밋

## 트리거와 단계 경계

- **"커밋해줘", "커밋 만들어줘", "커밋 계획 세워줘", "staged 변경 정리해줘"**: Phase 1만 수행한다. 커밋별 메시지·파일·이유를 제시하고 **승인을 기다린다**. 스테이징이나 커밋은 하지 않는다.
- **"커밋 계획 승인", "제시한 계획대로 커밋해줘"**: 직전에 제시한 계획이 있고 변경 범위가 그대로일 때만 Phase 2를 수행한다. 변경이 달라졌으면 다시 계획을 제시한다.
- 구현·푸시·PR 요청만으로 이 스킬을 실행해 커밋하지 않는다.

커밋 형식은 [Git 규칙](../../../../docs/conventions/git-convention.md)의 **커밋** 항목을 따른다. 형식은 `prefix(Class): 한국어 설명`이며, 여러 클래스를 한 번에 다루면 `(Class)`를 생략한다. 커밋 메시지에 AI 도구 서명을 넣지 않는다.

## 1. 범위와 비밀정보 확인

1. `git status --short --branch`, staged·unstaged **파일명**과 새 파일 목록을 확인한다. 이번 요청에서 만든 변경과 기존·무관한 변경을 구분한다.
2. 현재 브랜치가 `develop`이나 `deploy`이면 멈춘다. 단, README와 GitHub 이슈·PR 템플릿만 바뀐 경우는 `develop`에서 커밋할 수 있다.
3. 커밋 후보의 경로와 내용에서 `.env`, 인증서·개인키, 실제 비밀번호·API 키·토큰 값을 **노출하지 않고** 먼저 검사한다. `node scripts/security-source-audit.cjs`를 실행할 수 있다. 의심스러운 값이 있으면 파일명만 알리고 멈춘다.
4. 비밀정보 검사를 통과한 뒤 후보 diff를 검토한다. 기존의 무관한 변경은 스테이징하거나 되돌리지 않는다.

## 2. Phase 1 — 작은 커밋 계획

- 한 커밋은 **하나의 검토 가능한 변경 이유**만 담는다. 의존성·설정, Entity·Flyway migration, Service, Controller·DTO·API 문서, 문서는 분리 가능하면 각각 별도 커밋으로 계획한다.
- 각 커밋은 가능하면 그 상태로 빌드 가능해야 한다. 강하게 결합된 파일은 억지로 쪼개지 않는다. 모든 변경을 한 커밋에 넣는 통 커밋은 피한다.
- **커밋 번호, 메시지, 포함 파일, 변경 이유, 검증 결과**를 계획표로 보여준다. `git diff --check`와 변경에 맞는 검증을 수행하고, Java·설정 변경은 `./gradlew build`를 실행한다. 실패를 해결하지 못하면 원인을 보고하고 커밋하지 않는다.
- 계획을 보여준 뒤 승인을 기다린다. 승인 전에는 `git add`나 `git commit`을 실행하지 않는다.

## 3. Phase 2 — 승인된 커밋 실행

- `git status`와 후보 diff를 다시 확인한다. 계획 이후 변경이 생겼다면 수정된 계획을 제시한다.
- 승인받은 파일만 순서대로 스테이징하고, 각 커밋 전 `git diff --cached --check`를 확인한다. `git add .`와 `--no-verify`를 사용하지 않는다.
- `git log --oneline -n <커밋 수>`로 결과를 확인하고 커밋 해시, 포함 파일, 검증 결과를 보고한다.
- 푸시·PR·머지는 다음 사용자 명령 없이 진행하지 않는다.
